# WARDEN

**按行为特征识别并处置干扰性窗口的常驻看守。**

弹窗广告、流氓软件的推广窗、关不掉的悬浮球 —— 这些东西往往不是"一个窗口"的问题，
而是**一个会反复重建窗口的进程**。普通的"关闭按钮"对它无效，因为关掉一个它会再开一个。

WARDEN 的做法是：**看行为，不看良心。**

它不信任窗口自称的身份（标题、类名都能随便改），而是观察这个进程**做了什么**：
是不是短时间内疯狂新建窗口、是不是反复抢占前台、是不是被关掉又立刻回来。
分数够高才动手，动手也分等级 —— 先隐藏，再请求关闭，最后才考虑强制结束。

> **当前状态：Beta（0.1.0-beta.1）**
> 仅在本机测试，尚未发布。

## 它解决什么问题

| 常见做法 | 问题 |
| --- | --- |
| 按进程名杀 | 改个名字就绕过了 ✗ |
| 按窗口标题杀 | 标题留空就绕过了 ✗ |
| 一律强杀 | 容易误伤正常程序 ✗ |
| 手动关 | 它比你有耐心 ✗ |

WARDEN 换了个思路：

1. **行为评分** —— 不只看"它叫什么"，更看"它干了什么"
2. **分级处置** —— 能温和解决就不动硬手段
3. **有据可查** —— 每一步决策都写进日志，出问题能复盘

## 安全模型

这是本项目最重要的部分。**处置窗口是危险操作**，做错了会把系统搞崩。
所以 WARDEN 设了多道闸，任何一道拦住就不能强杀：

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 道：硬黑名单（41 条，不可配置）                        │
│     csrss / wininit / winlogon / services / lsass / smss /  │
│     svchost / dwm / explorer / System / Registry / …        │
│     ★ 这些进程无论多少个窗口，永远不强杀                     │
├─────────────────────────────────────────────────────────────┤
│  第 2 道：系统目录判定                                       │
│     映像路径含 \windows\system32\ / syswow64\ / winsxs\ /   │
│     servicing\ / boot\ / systemapps\ → 不强杀                │
├─────────────────────────────────────────────────────────────┤
│  第 3 道：数字签名判定                                       │
│     有合法签名的进程 → 只能隐藏或发关闭请求，不直接强杀      │
│     （签名状态未知 / 不受信任 / 已被篡改 → 一律保守对待）    │
├─────────────────────────────────────────────────────────────┤
│  第 4 道：进程白名单（用户可配）                             │
│     名单里的进程永不处理                                     │
├─────────────────────────────────────────────────────────────┤
│  第 5 道：用户授权（两段式弹窗）                             │
│     前四道都过了、但常规手段确实压不住 → 才问用户            │
└─────────────────────────────────────────────────────────────┘
```

### 关于"数字签名"

签名不代表"这是个好程序"，只代表"它没被篡改过"。
所以 WARDEN 对签名的处理是**降级**而非豁免：

- 有签名 → 只能隐藏 / `WM_CLOSE`，不能直接强杀
- 只有**明确无签名**的进程才允许强杀
- 用户明确授权后，有签名的进程也可以强杀（**由用户承担判断**）

### 关于"用户授权"

给用户的选项是**处置方式**，不是**安全判断**：

```
允许本次强杀   ——  这一次强制结束它
永久允许强杀   ——  以后遇到它直接强杀，不再询问
拒绝，继续尝试隐藏  ——  不用强制手段
```

WARDEN 不会问用户"这是不是恶意软件"（用户答不了），
只问"要不要用更硬的手段"（用户答得了）。

### 强杀之后又复活怎么办

如果某个程序**被强杀过又一次次出现**，说明强杀治标不治本。
这时弹窗的推荐会换成 **「永久允许强杀」**——
不是为了让你一直杀它，而是让它一冒头就被打掉，你好腾出手来**彻底卸载它**。

WARDEN 会在弹窗里引导你使用专业的卸载工具（Geek Uninstaller / Revo Uninstaller 等），
因为清除残留文件、注册表项、开机自启和计划任务，才是真正的解决方案。

### 启动自校验（防调包）

WARDEN 启动时会验证**自己**：

1. Authenticode 签名是否有效（被改一个字节就会失效）
2. 自身 SHA256 是否与配置里的基线一致

任何一项不过 → **拒绝运行**并留下日志。
这样即使本机被投毒替换，也能**拉停**而不是被感染。

调试时需要临时跳过：设环境变量 `WARDEN_SKIP_SELFCHECK=1`。

## 工作流程

```
   ┌──────────────┐
   │ 事件钩子      │  SetWinEventHook 监听窗口创建/显示/隐藏/前台切换
   │  + 100ms 巡检 │  兜底扫描，确保不漏
   └──────┬───────┘
          ↓
   ┌──────────────┐
   │ 行为评分      │  命中规则 + 抢焦点 + 置顶 + 无输入控件 + 短时间疯狂建窗 …
   │              │  ★ 用滑动时间窗，跑得久不会自动加分
   └──────┬───────┘
          ↓
   ┌──────────────┐
   │ 动手门槛      │  分数不够 → 什么都不做
   └──────┬───────┘
          ↓
   ┌──────────────┐
   │ L1 请求关闭   │  WM_CLOSE
   ├──────────────┤
   │ L2 隐藏+关闭  │  ShowWindow(SW_HIDE) + WM_CLOSE
   ├──────────────┤
   │ L3 强制结束   │  TerminateProcess（需过全部安全闸）
   └──────────────┘
```

**升级判据**：同一窗口多次处置无效 → 升一级。
**第二段弹窗**不是等固定时间，而是看"追不追得上"——
已经隐藏够多次但窗口数没减少，就立刻确认"常规手段失效"（通常几秒内）。

## 编译

### 环境要求

- **.NET 10 SDK**（含 Windows 桌面工作负载）
- Windows 10 / 11

### 编译本体（Native AOT）

```powershell
cd src
dotnet publish -c Release -r win-x64
```

产物：`src\bin\Release\net10.0-windows\win-x64\publish\WARDEN.exe`（约 3.5 MB）

> **为什么用 Native AOT**
> 体积小（3.5 MB vs 自包含 70 MB+）、启动快（约 50 ms）、无运行时依赖。
> 代价：WPF / WinForms 不可用（见下）。

### 编译设置工具

设置工具是**独立**的（因为 AOT 下 WinForms 不可用，见下方说明）：

```powershell
cd tools\settings
dotnet publish -c Release
```

产物：`tools\settings\bin\Release\net10.0-windows\win-x64\WARDEN-Settings.exe`

### 给产物签名（可选）

```powershell
# 首次：创建自签名代码签名证书
powershell -ExecutionPolicy Bypass -File <tools>\setup_codesign.ps1

# 每次编译后：签名
powershell -ExecutionPolicy Bypass -File <tools>\sign_files.ps1 -Path src\...\WARDEN.exe

# 验证是否被调包
powershell -ExecutionPolicy Bypass -File <tools>\sign_files.ps1 -Path <文件> -VerifyOnly
```

## 使用

### 首次使用建议

1. **先开着演习模式**（配置里 `protect.dry_run = true`，默认就是开的）
2. 正常用几天电脑，**看日志里它打算关谁**
3. 确认没有误伤 → 关掉演习模式

### 打开设置界面

双击 `WARDEN-Settings.exe`。它是独立窗口，不依赖 PowerShell 或控制台。

界面分六个标签页：

| 标签页 | 内容 |
| --- | --- |
| **规则** | 哪些窗口算"可疑"（进程名 / 标题关键词） |
| **保护** | 什么情况下不动手（前台窗口、有输入框…） |
| **处置** | 处置强度、分数门槛、弹窗参数 |
| **名单** | 白名单 / 永久允许强杀 / 强杀历史 |
| **安全** | 启动自校验开关、期望哈希、硬黑名单查看 |
| **日志** | 最近日志、打开日志目录 |

底部按钮：**保存配置** / **重新加载** / **启动 WARDEN** / **停止 WARDEN**，以及实时状态。

> 配置改完保存即可，WARDEN **每轮都会重新读取**，不用重启。

### 日志

位置：`%LOCALAPPDATA%\dsh-tools\WARDEN.log`

日志里能看到每一次决策的**完整理由**，例如：

```
[评分] 66 python.exe 「某弹窗」 命中规则「推广窗」(+40) 抢占了前台焦点(+12) 无输入控件(+8)
[决策] python.exe 尝试=2 失败=2 门槛=2 reachedFirst=True canAsk=True
[L2 隐藏+关闭] 分数=81 python.exe 「某弹窗」 ★受保护进程，不用强杀（累计尝试 2 次）
[弹窗] ★ python.exe 之前被强杀过，现在又出现 → 判定为【复活】
[★用户授权] python.exe —— 允许强制结束（永久）
[L3 强杀] 分数=81 python.exe (pid=2380) 耗时=12841ms 结果=成功
```

## 配置说明

配置文件：`%LOCALAPPDATA%\dsh-tools\WARDEN.json`

主要字段：

| 字段 | 含义 | 默认 |
| --- | --- | --- |
| `rules[].title_contains` | 标题包含这些词就命中 | — |
| `rules[].process` | 进程名匹配 | — |
| `protect.dry_run` | ★ 演习模式（只记日志） | `true` |
| `protect.skip_if_foreground` | 前台窗口不处理 | `true` |
| `protect.skip_if_has_edit` | 含输入框不处理 | `true` |
| `action.allow_terminate` | 允许强制手段 | `false` |
| `behavior.apply_threshold` | 动手门槛（分数） | `55` |
| `behavior.terminate_threshold` | 强杀门槛（分数） | `75` |
| `action.consent_after_failures` | 失败几次后弹窗 | `6` |
| `action.second_stage_min_hides` | 隐藏多少次后判定"追不上" | `8` |
| `action.second_stage_max_wait_ms` | 第二段兜底等待 | `6000` |
| `process_whitelist` | 永不处理的进程 | `[]` |
| `consented_processes` | 永久允许强杀 | `[]` |
| `terminated_history` | 强杀历史（用于检测复活，可清空重置） | `[]` |
| `expected_self_hash` | 自身 SHA256 基线 | `""` |
| `self_check_on_start` | 启动自校验 | `true` |
| `self_check_block_on_fail` | 自校验失败时拒绝运行 | `true` |

### 几处值得说明的设计取舍

**为什么设置界面单独编译？**
主程序用 Native AOT，而 **WinForms 在 AOT 下不可用**（依赖运行时反射与 COM 互操作）。
设置界面只在用户点开时才运行，不需要 AOT 的体积和启动优势，
所以单独编译成普通 exe，两者解耦。

**为什么弹窗用 `TaskDialogIndirect` 而不是自绘窗口？**
自绘窗口需要自己管 `RegisterClassW` / `CreateWindowExW` / 消息循环，
实测在 AOT 下出现过"窗口创建成功但不可见"的诡异问题。
`TaskDialogIndirect` 是 comctl32 的原生任务对话框，
自带消息循环与模态行为，还原生支持**命令链接**（大按钮 + 主文字 + 说明文字），
正好满足"按钮用词要明确"的要求。
★ 它需要 comctl32 **v6**，所以 `app.manifest` 里的依赖声明是必需的。

**为什么评分用滑动时间窗？**
早期版本用累计计数（"这个进程一共创建了 N 个窗口"）判断，
结果是**跑得越久的正常程序分越高**，而刚启动的流氓软件反而分不够。
改成只统计"最近 10 秒内"的行为后，既准确又不会随时间漂移。

### 为什么是 AGPL 而不是 GPL

GPL 的"开源义务"只在**分发**时触发 ✗

   就能完整绕开 GPL，一行代码都不用开源 ✗✗

AGPL 第 13 条（Remote Network Interaction）把触发点扩展到**通过网络交互** ✓
→ 谁把 WARDEN 做成在线服务，谁就必须把源码提供给用它的用户 ✓
→ 这对本项目的意义：拦截规则与判定逻辑是**用户能看见、能审计**的，
   不会被某个"云版 WARDEN"黑箱拿走 ✗
