# WARDEN 设计说明

本文说明 WARDEN 的**核心设计取舍**和**踩过的坑**。
如果你要改这个项目，建议先读这里。

---

## 一、核心思路

### 为什么"看行为"而不是"看身份"

窗口的身份信息**全部可以伪造**：

| 身份信息 | 怎么被绕过 |
| --- | --- |
| 进程名 | 改个文件名就行 |
| 窗口标题 | 留空，或随机生成 |
| 窗口类名 | 注册成 `#32770`（系统对话框的类名） |
| 数字签名 | 用别的合法程序当宿主来弹窗 |

所以 WARDEN 的判断依据是**这个进程干了什么**：

- 短时间内疯狂创建新窗口
- 反复抢占前台焦点
- 被隐藏后立刻又显示出来（**隐藏对抗**）
- 被关掉又立刻重建
- 用系统对话框类名 / 留空标题（**这本身就是可疑信号**）

这些行为**没法伪装** —— 要弹广告就必须真的弹出来。

### 评分用滑动时间窗，不用累计值

**踩过的坑：**

早期版本用累计计数判断，例如"这个进程一共创建了 47 个窗口 → 可疑"。
问题是：

```
程序跑 1 小时  →  累计 47 个窗口  →  加分 ✗
程序跑 1 分钟  →  累计  3 个窗口  →  不加分 ✗
```

结果**跑得越久的正常程序分越高**，刚启动的流氓软件反而分不够。
这是典型的"累计量当强度用"的错误。

改成只统计**最近 10 秒内**的行为后：

```csharp
public int RecentNewWindows() => RecentCreateTicks.Count;   // 只数窗口内的
```

既准确，又不会随时间漂移。

### 顺手加的两条启发式

1. **新出现的进程 + 行为异常** → 额外加分
   弹窗广告的典型特征就是"突然冒出来"，而正常程序往往开了很久。

2. **标题为空** → 额外加分
   正常用户界面几乎都有标题。有窗口、有类名、却故意留空，
   是为了绕开标题匹配 —— 这个信号本身就有价值。

## 二、安全设计

处置窗口是危险操作。WARDEN 的原则是：**宁可漏，不可错**。

### 五道闸，任何一道拦住就不能强杀

```
硬黑名单（41 条）→ 系统目录 → 数字签名 → 进程白名单 → 用户授权
```

### 签名 = 降级，不是豁免

用户明确要求过："有合法数字签名的，也不能一概而论"。

所以 WARDEN 对签名的处理是：

- **有签名** → 只能隐藏 / `WM_CLOSE`，不能直接强杀
- **明确无签名** → 允许强杀
- **状态未知 / 不受信任 / 已被篡改** → 一律保守对待

**并且**：用户明确授权后，有签名的进程也可以强杀。
理由是 —— 用户**已经知道并接受了**这个决定，属于知情同意。

### 给用户的是"手段选择"，不是"安全判断"

```
✓ 允许本次强杀 / 永久允许强杀 / 拒绝，继续尝试隐藏
✗ 这是不是恶意软件？
```

第二种用户答不了，第一种用户答得了。

---

## 三、两段式授权弹窗

设计目标是：**第一次就解决问题，不要反复打扰用户。**

### 第一段

常规手段失败 N 次后弹出。选项：

```
允许本次强杀     这一次强制结束它
永久允许强杀     以后遇到它直接强杀，不再询问
拒绝，继续尝试隐藏  不使用强制手段
```

### 第二段

用户选了"继续隐藏"，但**确实压不住**时再弹一次。
这次是为了确认"常规拦截已经完全失效"。

**★ 判据不是等固定时间**，而是看"追不追得上"：

```
已隐藏 ≥ N 次  且  该进程窗口数【没有减少】
    → 追不上 → 立刻确认失效（通常几秒内）
```

**踩过的坑：** 最早写死"等 15 秒"。

- 工具其实压得住 → 用户白等 15 秒 ✗
- 工具真压不住 → 也要等满 15 秒才知道 ✗

改成"追不上"判据后，2~3 秒就能出结论。

### 复活检测

```
程序被强杀过 → 记进 terminated_history
它又出现了   → 判定【复活】
             → 弹窗推荐从「立即强杀」改成「永久允许强杀」
```

**为什么改推荐？**

强杀一次它还会回来，用户来不及卸载。
永久强杀能让它一冒头就被打掉，**用户才有时间从容卸载**。

所以「永久允许强杀」的定位不是"懒得管"，而是**配合卸载的过渡手段**。

弹窗里会明确引导使用专业卸载工具（Geek Uninstaller / Revo Uninstaller 等）。

## 四、踩过的坑（重要）

### 坑 1：计数逻辑被提前 `return` 绕过

```csharp
if (canAsk) { ...弹窗... }
else {
    return ActHide(w, score);   // ★ 直接返回
}
// ★★★ 计数代码在【这之后】✗ 永远执行不到
```

**现象**：日志里 606 次"隐藏+关闭"，但**一次弹窗都没有**。
**修法**：把计数放进 `ActHide` 内部。

### 坑 2：`Prune` 用"可见窗口"判断进程存活

```csharp
engine.Prune(alivePids);   // alivePids 来自【可见窗口】
```

但工具的动作**就是让窗口不可见** ✗
→ 隐藏后 `Prune` 认为进程没了 → 删掉档案 → 计数每轮归零
→ 弹窗门槛永远到不了 ✗

**修法**：计数改在 `ActHide` 里直接维护。
**教训**：统计口径和工具的核心动作**不能互相破坏**。

### 坑 3：静默 `return` 让问题无法定位

```csharp
if (hwnd == IntPtr.Zero)
{
    return ConsentAnswer.KeepHiding;   // ★ 连一行日志都没有
}
```

外部只看到"没弹窗"，看不到**为什么**没弹窗 ✗
**修法**：所有提前退出都必须留日志。
**这条已经写成规范**（见下方"日志规范"）。

### 坑 4：`TaskDialogIndirect` 找不到入口点

```
EntryPointNotFoundException: TaskDialogIndirect, comctl32
```

**原因**：这个函数**只在 comctl32 v6 里存在**，
而 .NET 进程默认加载 v5 ✗
**修法**：加 `app.manifest` 声明 comctl32 v6 依赖。
**★ 这个异常正是靠日志抓出来的** —— 否则又得猜好几轮。

### 坑 5：自绘窗口"创建成功但不可见"

自绘 `RegisterClassW` + `CreateWindowExW` + 自己写消息循环时，
出现过日志显示"窗口已创建 hwnd=xxx"，但 `EnumWindows` 里找不到它，
用户看到"闪一下就没了"的情况。

**结论**：AOT 下自绘窗口的坑很深。
**改用 `TaskDialogIndirect`** —— comctl32 原生实现，自带消息循环与模态行为，
一次就通了。而且它原生支持**命令链接**（大按钮 + 主文字 + 说明文字），
正好满足"按钮用词要明确"的需求。

### 坑 6：`WinVerifyTrust` 返回"无签名"不代表真的没签名

改一个字节后自校验报"自身未签名"，这是**不准确的**：

- 改的字节落在 PE 的**证书表区域** → 签名数据本身被破坏
- `WinVerifyTrust` 返回 `TRUST_E_NOSIGNATURE` 而不是 `TRUST_E_BAD_DIGEST`

**修法**：读 PE 可选头的 `DataDirectory[IMAGE_DIRECTORY_ENTRY_SECURITY]`（索引 4）。
`VirtualAddress`/`Size` 非 0 就说明**文件里有签名数据**，
此时 `NOSIGNATURE` 应归类为"被篡改"而非"没签名"。

## 五、日志规范

**用户立下的规矩：每个程序都必须有日志。**

本项目遵守以下几条（缺一不可）：

| # | 要求 |
| --- | --- |
| 1 | 每个条件分支都要能回答"为什么走这条路" |
| 2 | ★ **禁止静默 `return`** —— 任何提前退出都要留日志 |
| 3 | 每个失败都要记**错误码**（`Marshal.GetLastWin32Error()`） |
| 4 | 启动时写下**配置摘要** |
| 5 | 决策点记录**输入值 + 输出** |
| 6 | 异常要带完整堆栈 |
| 7 | 日志分级（错误/警告/决策/步骤/状态） |
| 8 | 日志位置固定、可预期 |
| 9 | 提供"一键看日志"入口 |
| 10 | 宁可多记，不可少记 |

日志里的每条决策都长这样：

```
[决策] python.exe 尝试=2 失败=2 门槛=2 reachedFirst=True canAsk=True
```

一眼就能看出"门槛到了没有"，而不是靠猜。

## 六、技术约束（Native AOT）

主程序用 Native AOT 编译。这带来几个**硬约束**：

| 不能用 | 原因 |
| --- | --- |
| WPF / WinForms | 依赖运行时反射与 COM 互操作 ✗ |
| FlaUI（UI 自动化） | COM 互操作，运行时抛 `InvalidProgramException` ✗ |
| 运行时 C# 编译 | 需要动态代码生成 ✗ |
| `Marshal.PtrToStructure(nint, Type)` | 用泛型版 `PtrToStructure<T>()` 代替 |

**能用的**（已实测）：

- ✓ 纯 Win32 P/Invoke
- ✓ `System.Text.Json` 源生成器
- ✓ `TaskDialogIndirect`（comctl32）

**收益**：产物 3.5 MB（自包含要 70 MB+），启动约 50 ms。

**代价**：设置界面只能单独编译（因为要 WinForms）。
这个取舍是刻意的 —— 设置界面只在用户点开时运行，不需要 AOT 的优势。

## 七、红队测试

项目自带一套对抗测试（在 `诊断\sandbox\popup-lab\`，不在本目录内）。
Ultra 版包含 10 个**专门针对本工具**的绕过手段：

| # | 攻击手法 | 打的是哪道防线 |
| --- | --- | --- |
| U1 | **隐藏对抗**：被隐藏后立刻 `Show` 回来 | 隐藏策略 ✗ |
| U2 | 50ms 一次 `Show`/`Hide` 振荡 | 可见性统计 ✗ |
| U3 | 多进程守护（A 被杀，B 重启 A） | 单进程强杀 ✗ |
| U4 | 伪装成 `svchost.exe` | 进程名匹配 ✗ |
| U5 | 类名伪装成 `#32770` | 类名匹配 ✗ |
| U6 | **标题留空** | 标题匹配 ✗ |
| U7 | 完全模仿正常程序 | 尺寸/位置启发式 ✗ |
| U8 | 弹窗放到屏幕外 | 位置判断 ✗ |
| U9 | 全力规避行为分 | 评分模型 ✗ |
| U10 | 秒级重建 40 个窗口 | 处置速度 ✗ |

**U1 是最狠的** —— 它直接打废"隐藏"这个核心手段。
实测结果是：隐藏 2 次后升级到 L3 强杀，压制成功 ✓

**U6 打穿过一次** —— 空标题窗口完全看不见。
修法是：空标题窗口也纳入评估（但只能靠行为分判定），并额外加权。

## 八、如果你要改这个项目

**改之前请确认：**

1. 新加的判断不会让**正常程序**被误伤（跑一遍误杀率测试）
2. 不会削弱安全闸（硬黑名单 / 系统目录 / 签名判定）
3. 每个新分支都有日志
4. 跑一遍红队 Ultra（尤其是 U1 和 U6）

**最危险的三件事：**

- ✗ 把硬黑名单改成可配置
- ✗ 放宽"签名进程不强杀"的限制
- ✗ 在守护检测里连坐杀掉守护进程（它可能是计划任务或系统服务）
